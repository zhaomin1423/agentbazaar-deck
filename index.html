第一幕 · 背景｜现状

没有这个网络，agent 是这样"凑能力"的

问 agent「查个天气」的三种真实结局

凭记忆硬答——用训练数据里的"今天"作答：过期，甚至是幻觉
现场猜 API——自己写 curl 调公开接口：端点、参数、鉴权全靠猜，失败或错数，用完即弃不可复用
联网搜网页——读回碎片文本，不是结构化的实时数据

agent 从不说"我没有工具"——它即兴发挥。缺的不是答案，是可信的答案来源：每次从零拼凑，好的能力无法沉淀复用。

当用户决定"给它装个工具"

Google / 社群提问 → 翻 awesome 清单赌一个 → 抄 JSON、申请 key、手改宿主文件 → 无扫描无评测，投毒失效自担 → 更新不知、换机重配（30 分钟 – 数天）

今天的找法结构性缺陷
搜索引擎 + 社群提问人肉过滤；结论随博客过期
awesome 清单 / 目录站静态列表：无语义检索、无信任评分
官方 MCP Registry仅 MCP 一态；无中立评测
大厂各自广场围墙互不联通，重复入驻 N 家

共同缺失的一环：agent 运行时没有一个可信的"能力发现"动作。

第二幕 · 方案｜能力闭环

能力闭环：知所需 · 荐所信 · 予所用 · 伴所长

知所需agent 自知缺口 · 双触发
→
荐所信证据簇 · why · 风险翻译
→
予所用征得同意 · 一键装备
→
伴所长护航 · 同步 · 长养

知所需 —— 用户只说任务

"帮我查询明天的天气"，不提"服务"二字：agent 在能力盘点中发现缺口，自动进入发现流程；显式查询同轨同管线。

荐所信 —— 不可信的进不了结果

推荐即背书：候选自带五源信任证据与推荐理由；风险如实翻译（样本量 / 新鲜度 / 权限），未评测显著标注。

予所用 —— 从候选到装备一步完成

征得同意后写入宿主（MCP 配置 / skills 目录 / plugin 整包）：写前备份、dry-run 可预览、鉴权引导随行。

伴所长 —— 装上之后才是服务的开始

安全公告与一键卸载、危险更新先确认、跨环境同步、版本策略（锁版 / 随新）——能力持续在线，信任持续在场。

第二幕 · 方案｜检索引擎

荐所信的引擎：召回 → 融合 → 聚簇 → 解释

  • 四通道召回：词法（BM25）· 语义向量（pgvector）· 能力标签 · 容错（trigram）
  • RRF 融合 + 多因子排序：相关性 0.35 · 信任 0.25 · 热度 0.20 · 维护 0.10 · 兼容 0.10
  • 按服务聚簇折叠：同服务多形态/第三方封装 → 一簇（primary + alternatives）
  • 多样性与冷启动：发布者上限防霸屏；探索配额给新服务曝光
  • 可复现：响应携带 ranker 版本与权重——任何实例同一排序

质量不是形容词

"质量最佳" = 机器可验证的信任证据 + 真实安装统计——服务可以实测，不必像网页那样间接推断。

{
  "clusters": [{
    "service": "amap/maps",
    "primary": { "id": "bazaar://amap/maps",
      "trust_score": 87,
      "why_matched": [
        "语义相关性 0.91",

    "alternatives": [
      { "id": "…/maps-skill",
        "note": "同服务 skill 形态"}]

}

第二幕 · 方案｜信任体系

TrustScore：审核方法即信任本身

我们不生产服务，我们为服务锻造信任——每一分都来自可复现的机器证据。

五源证据（每版本重跑）说明
静态扫描 scansemgrep / gosec / gitleaks + SBOM 依赖供应链扫描
沙箱实测 sandbox隔离环境真实调用：功能通过率 / p95 / 失败率 / 失败模式与副作用画像 / 声明诚实度（宣称 vs 实测）
来源 provenanceSigstore 签名 + SLSA 出处
活性 liveTop 5000 每 5 分钟探测
维护 maintenance发版频率与仓库活跃

条件化信任

分数按使用条件分维度呈现：模型规模、权限范围、运行环境——企业允许清单作为硬过滤前移（装不上的不进结果）。

恶意服务三段防线

准入（验证/扫描/未评测降权标注）→ 运行（diff 冻结/行为复检）→ 处置（状态机 + 安全公告 SLA：critical 2 小时冻结 24 小时公告 + 一键卸载）。

第二幕 · 方案｜信任的呈现

诚实的分数：把证据、样本与新鲜度一起给用户

每个分数自带三件事

  • 证据来源：这一分来自哪些机器检测
  • 样本量：实测调用次数、时间窗口
  • 新鲜度：距上次复测多久——超期显示"待重测"而非旧分

一句话风险翻译

不给用户一个裸数字。87 分旁边写着：

⚠ 需要 API key · 上次实测 2026-10-28（3 天前）
  · 声明 12 个工具，实测 11 个可用
  · 高权限：文件系统只读

中立红线（写进治理）

TrustScore 算法与权重开源、任何实例可复现同一分数 · 自然排序与信任分永不出售 · 验证失败降权而非黑箱下架 · 排序变更走 RFC 与版本化留痕。

第二幕 · 方案｜身份体系

一次登录，全网服务免注册（可选，不强制）

  • 统一账号：微信 / 支付宝 / 飞书 / GitHub 联合登录；浏览检索免登录
  • AgentBazaar 登录（OIDC IdP，可选）：面向不想自建账号的小开发者——用户一次授权，服务拿到经验证身份
  • KA 零改造：已有账号体系的服务保持自有认证，平台做联邦适配
  • 凭证保险库：存量 API key 加密托管，安装时自动注入
  • agent 身份：非人类主体 + 委托授权链（user → agent → service），可审计可撤销——微信登录没有的能力

红线：claims 最小化 · 身份数据不进排序、不售卖 · 授权管理页随时撤销。

对人human

一个账号管理全网授权；授权页随时查看、撤销任何服务。

对 agentnon-human principal

平台签发 agent 身份，代表用户行事的每一步有 scope、期限、审计与撤销。

类比

微信/支付宝登录之于网站 —— 我们之于 agent 服务；且把"机器用户"作为一等公民。

第二幕 · 方案｜解决什么问题

四类角色：之前 vs 之后

角色之前有了 AgentBazaar
agent即兴拼凑（过期知识 / 猜 API），或把配置甩给用户任务在，能力到：自动发现可信服务，一键装备，好的能力沉淀复用
人类用户每个服务注册一个账号、每台机器配一遍一个账号、一次同步：全网服务与全部环境就绪，授权随时可撤
提供方（小开发者）做了服务没人看得见，还要自建账号与分发一条命令发布，触达所有 agent 宿主；可选免建用户体系
提供方（KA）每个 agent 生态重复接入，数据分散一次接入全渠道：品牌页与联邦互通，自有账号零改造
企业服务进内网无治理，审计难以交付私有市场 + 策略 + 审计，数据不出内网，合规即出厂配置

同一个网络，四类角色各自拿到结构性改善——这是双边市场 + 基础设施的双重形态。
